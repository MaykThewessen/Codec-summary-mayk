Ratio, speed, and
where each one wins

Every compressor argument is the same argument: how small, how fast to write, how fast to read. Two of those you can have. The third is what you are choosing when you pick a tool and a level, and the answer moves depending on what you are compressing.

zstd -19 --long
Large datasets and backups where you still want the restore to finish. Within a few percent of xz on ratio, and it reads back roughly faster. --long=27 widens the match window to 128 MB, which is what finds the redundancy between near-identical files in a big tarball.

The default answer
zstd -6
Where most real work belongs. Compresses about as well as gzip -9 while compressing several times faster, and decompresses several times faster than gzip on top of that. If you are replacing gzip anywhere and do not want to think about it, this is the setting.
tar -I 'zstd -6 -T0' -cf out.tar.zst dir/
64 kB window
lz4 -9 (HC)
A hot path that still wants the data smaller: message queues, RPC payloads, in-memory column blocks. The high-compression mode is slow to write and identical to read, so it fits anything written once and read constantly.

gzip -6
Not because it is good. Because DEFLATE is in every language runtime, every browser, every embedded toolchain and every twenty-year-old appliance you have to interoperate with. When the receiver is unknown, this is the floor, and zip is the same coder in a different envelope.

The flag worth knowing

Long-range matching, on data that needs it

A compressor can only reuse what fits inside its match window. gzip's window is 32 kB; zstd's default is a couple of megabytes; xz -9 carries a 64 MB dictionary, which is a large part of why it wins on ratio and why it is so slow. --long=27 gives zstd a 128 MB window with a cheap long-distance matcher in front of it, and on data with far-apart repeats it changes the answer entirely.

A distinction worth making

zip, 7z and RAR are containers, not codecs

gzip, zstd, brotli, xz and lz4 are compressors: bytes in, bytes out. zip, 7z and RAR are archive formats that bundle a directory, store names, permissions and checksums, and then call a compressor on the contents. Comparing "zip versus zstd" compares a filing cabinet with a hydraulic press. The interesting question is which compressor a container uses and whether it compresses the files together or one at a time.

The same source files, packed seven ways

Solid means the whole stream is compressed at once, so matches can cross file boundaries.

zip

DEFLATE per member, by default. That per-member choice is what makes it random-access (you can extract one file without reading the archive) and what makes it larger. Modern zip can carry other coders including bzip2, LZMA and zstd, but a .zip produced by anything you are likely to receive is deflate.

7z

LZMA2 by default, solid by default, which is exactly the pair that makes it beat zip so heavily on directories of similar files. The coder inside it is the same one xz uses, so 7z and tar.xz land within a rounding error of each other, as the table shows.

RAR cited, not measured

No RAR encoder exists in this container and none is freely licensed, so RAR is absent from every chart on this page rather than estimated. Published comparisons put RAR5 between 7z and zip on ratio, with a proprietary encoder, a paid licence for compression, and no advantage that survives the existence of zstd and xz. Its remaining reason to exist is that somebody sent you one.

The constraint nobody checks

What the reader has to hold in RAM

Ratio and speed are what benchmarks report. Memory is what breaks things: a codec's match window has to be resident on both sides, so the setting that squeezes hardest also demands the most from whatever has to open the file. That includes phones, embedded devices, browser tabs, and any server holding thousands of streams open at once. The window column is the number that travels with the file.

Corrections and confirmations

Received wisdom, checked against the measurements

Holds up
"zstd is Meta's, and its decompression is very fast."

Right, with a caveat
"zstd at -9 or higher is efficient."

Holds up
"xz is the one the Linux distributions use."

Half a category error
"gzip/zip, zstd, 7z, xz and RAR."

Three of those five are compressors and two are archive containers. gzip and zip are the same coder: DEFLATE, one as a stream and one as a filing format. 7z is a container whose default coder is LZMA2, which is the coder xz is a stream format for, so "7z versus xz" is mostly a question of envelope rather than compression. RAR is a container with its own proprietary coder. Sorting the list into two columns makes the choice much easier: pick the coder on the evidence, then pick the container on what the receiver needs to open it.

Not measured here
"RAR/WinRAR."

There is no freely licensed RAR encoder, and none is installed in this container, so no RAR number appears anywhere on this page. Every figure here comes from an encode run on this machine; a cited RAR ratio would be the only exception and it would sit next to numbers it was never measured against. Treat published RAR comparisons as directional at best, since they rarely control for corpus.

True, and usually the wrong lever

Operational

What to actually type

Six situations, and the setting that measured best in each on this hardware.

Tarballs and directory archives

# the modern default: near-xz ratio, reads back many times faster
tar -I 'zstd -19 -T0 --long=27' -cf release.tar.zst dist/

# when the receiver is unknown or ancient
tar -czf release.tar.gz dist/          # deflate, decodes everywhere

# when the file will be downloaded far more often than built
XZ_OPT=-9e tar -cJf release.tar.xz dist/   # slowest to write, smallest result

HTTP responses

# static assets: precompress at build time, serve the file as-is
brotli -q 11 -o app.js.br app.js
zstd  -19 -o app.js.zst app.js         # if your CDN negotiates zstd
gzip  -9 -k app.js                     # the fallback that is always accepted

# dynamic responses: compress per request, so the encoder has to be cheap
#   nginx: brotli_comp_level 4-5, or zstd -3
#   never brotli -11 or zstd -19 on the request path

Long-term archives and backups

# smallest, if the restore can be slow and the reader has the RAM
XZ_OPT=-9e tar -cJf archive.tar.xz data/

# within a few percent, and restores far faster: usually the better trade
zstd -19 --long=27 -T0 archive.tar

# check the decoder side before committing to xz -9
xz --robot -lvv archive.tar.xz | grep memory

Hot path, in memory

# written once, read constantly: lz4 high-compression
lz4 -9 pages.bin pages.lz4

# written and read constantly: lz4 default, or zstd -1 if you want the ratio
lz4 -1 buffer.bin buffer.lz4

Parquet and time-series work

# zstd is the right default inside a columnar file. the codec runs per
# page, so the level buys much less than it does on a whole-file encode.
pq.write_table(tbl, "prices.parquet", compression="zstd", compression_level=3)

# the encoding matters more than the codec: dictionary-encode low-cardinality
# string columns and use the smallest numeric type that fits, first.
pa.array(zones).dictionary_encode()

# do NOT then compress the parquet file again
gzip prices.parquet                    # measured gain: see the corpus chart

Someone sent you an archive

7z x thing.7z          # p7zip, reads 7z, zip, xz, and rar with the extra codec
unar thing.rar         # unarchiver: free RAR decoder, no encoder
bsdtar -xf thing.zip   # libarchive reads essentially all of them
Method

How these numbers were produced, and where not to trust them

Throughput here is noisy

Single-threaded, one buffer

Every encode is one thread on one in-memory buffer. Real zstd -T0 and xz -T0 split the input across cores and get most of a linear speed-up, which changes the compression-speed picture but not the ratio and not the decompression speed. Multi-threading also costs a little ratio, because the blocks stop sharing history.

Two corpora are generated

The log and time-series corpora are synthesised, because no permissively redistributable real equivalent exists. Their statistical shape is the point and it is reproduced honestly, but a real log stream with more entropy in its message bodies would compress somewhat less well than the one here.

Decompressor memory is declared, not measured

Compressor peak is a real measurement. The decompressor side is not: these libraries allocate their window lazily out of heap the process had already faulted in, so the peak-RSS delta read zero even for codecs with an 8 MB window. The window each file declares in its own header is reported instead, which is the number a reader is actually constrained by.

Scripts and raw measurements live in the repository beside this page, so every figure can be regenerated or argued with.

ratio = input bytes / output bytes  ·  throughput = input bytes / elapsed seconds  ·  median of rounds
